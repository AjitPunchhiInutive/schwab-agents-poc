Agent Gateway Architecture

APM-lookup agent → Agent Gateway → Cloud SQL MCP server → Cloud SQL for PostgreSQL.

The three layers stack — you use all of them. Agent Identity says who is calling (the agent gets its own SPIFFE ID + auto-rotated X.509 cert, and is its own IAM principal). Agent Gateway decides whether the call is allowed (a managed proxy that checks identity, registry, and IAM before forwarding). Model Armor checks what's in the payload (prompt injection, sensitive data) — it isn't an alternative to the gateway, it's a policy the gateway runs inline.

Inside the gateway: the egress checks in order

When the agent calls execute_sql, the gateway walks this sequence. The first stage that fails returns a 403 to the agent; cheap identity and registry checks run before payload inspection.

Semantic policies, spelled out

IAM and the registry answer a static question — can this agent reach this tool? — and the answer is the same for every call. Semantic policies evaluate the individual call in context: what the agent is about to do, whether it matches what the user actually asked for, and whether the sequence of tool calls is dangerous even when each call is individually allowed. For this flow, the ones worth writing:

  • Statement-shape rule: only SELECT statements through execute_sql. IAM can't see the SQL text; a semantic policy can, and blocks an UPDATE or DROP even though the tool itself is allowed.
  • Intent match: the user asked about one APM ID, so the query must filter on that APM ID. Catches a compromised or confused agent querying unrelated rows or other tables while "answering" a legitimate question.
  • Toxic tool combinations: a database read followed by any external-send tool (email, webhook, another MCP server) in the same plan is an exfiltration pattern — block the combination, even though each tool is individually permitted.
  • Scope limits: no SELECT * or WHERE-less queries — a lookup agent has no reason to page through the whole table, so a bulk read is treated as anomalous and denied.

Inside the gateway: the ingress path

The ingress pipeline is deliberately shorter than egress, and the asymmetry is the point: on the way in, the gateway authenticates the client and screens the content — it does not authorize. There is no IAM×IAP stage here; "who may invoke this agent" is enforced by IAM at the agent's own endpoint, after the gateway. Authentication uses three-legged OAuth: the user, the client app, and the identity provider complete the sign-in before the gateway is ever called — the gateway only validates the resulting access token. Because a 3-legged token carries the user's identity (not just the app's), it is also what makes per-user data authorization possible downstream.

Don't forget the database side

  • Enable cloudsql.iam_authentication and add the agent as an IAM database user — no passwords anywhere.
  • Set data_api_access = ALLOW_DATA_API (required by the managed MCP server).
  • execute_sql runs whatever SQL the DB user is allowed — so GRANT SELECT on only the APM table is your real write-protection, not the gateway.
